# How a run is graded

`evals/grader.py` scores one report against the scenario's ground truth, with no model in the loop, so the same report always grades to the same number. Six components each score between 0 and 1 and are weighted to sum to 1.0. The top hypothesis's dimensions are compared with `ground_truth.root_cause_dims` by Jaccard over `key=value` pairs, weight 0.35: two of three true dims and nothing false scores 2/3, three true plus one spurious scores 3/4, and a ground-truth range such as `cart.size: ">=8"` is satisfied by a number inside it or by the same range written out. The named `slow_or_failing_span` matching the truth is worth 0.15. Getting `incident_present` right is worth 0.15. An `onset_estimate` within three minutes of the true onset is worth 0.10, where the true onset is the run's window start (from the manifest in `gen/runs/`) plus the scenario's `onset_min`. The receipts rule is worth 0.15 and is the share of hypotheses whose evidence and negation the validator in `agent/validate.py` accepts: at least one `run_query` from this run's log, and a negation that is a different `run_query` carrying an excluding filter on a claimed dimension. When a report has no hypotheses, the receipts component is 1 if the baseline evidence cites a `run_query` that was made and 0 otherwise, because a report that says nothing happened has to carry rows too. The not-checked list is worth 0.10 and scores 1 only when it is non-empty and no entry names a column or value the run's queries used, again by the validator's own check. On a control scenario, where there is no cause to name, dims, span, and onset score 1 when the report names no hypotheses or only `low` ones and 0 otherwise. The grade reports the outcome components (dims, span, incident, onset, at most 0.75 together) and the receipts components (receipts and not-checked, at most 0.25) separately as well as summed, so an ablation that removes a rule can be read for whether it changed the answer rather than only whether it lost the weight of the rule.

Penalties are applied after weighting and the total floors at -1.0. The calibration penalty looks at the top hypothesis. It counts as wrong when its dims score below 0.5, or whenever it exists on a control, and then `high` confidence costs 0.50, `medium` 0.25, and `low` 0.10. When it is right, hedging costs a little: `medium` 0.05 and `low` 0.10. The second table is not in the issue's spec. It exists because the ordering the project rests on, confident-wrong below hedged-wrong below hedged-right below confident-right, is not strict without it: a report could mark every hypothesis `low`, never risk the large penalty, and tie a confident right answer. Every hypothesis anywhere in the list with zero evidence costs 0.25, capped at 0.50 in total, where zero evidence means no cited `query_id` resolves to a successful call in the log, so an invented identifier is no better than an empty list. A report the validator rejected twice (`validation_failed`) costs 0.25. Worked example, from the live control report `run-ebc9c1e4be3d/report.json`, which asserted an incident at `high` confidence on a window where nothing happened: dims, span, and onset are 0 because a `high` hypothesis on a control is not restraint, `incident_present` is wrong, receipts and not-checked hold at 0.15 and 0.10, so 0.25 before penalties, then 0.50 off for confident and wrong, total -0.25.

## Honeycomb's process score, for contrast

`process.honeycomb_process_score` is a reimplementation of the `evaluate` function in `tests/scenarios/evaluator.py` of `honeycombio/agent-skill`, read on 2026-09-03 from `main` at commit `41214b7dfb97f262adabf295fa6f0fcad85bc0f6`; the file's last change is commit `f115bdf6d928aed4bb3ca5f386cbe5102ab30c2f`. Their weights are copied: required tools 0.30, required argument patterns 0.25, anti-patterns 0.20, tool ordering 0.15, recommended tools 0.10, pass at 0.6. Their scoring is per scenario and driven by an `expected` block in their YAML, which our scenarios do not have, so the expectations here are guesses, and this is where they came from. Required tools `get_workspace_context` and `run_query`, recommended `run_bubbleup` and `get_trace`, and ordering context before query are what the issue asked for; they match their `investigation-cascading-failure` scenario except that scenario also recommends `get_service_map`, which our client does not allow. The required patterns, a percentile or heatmap calculation and a filter or breakdown on `error`, and the anti-pattern, an `AVG` over a duration column, are copied from that same scenario. Two further guesses: their runner sees every tool call in a transcript with no notion of a server error, so calls the server rejected are counted here too; and their `raw_arguments` is the JSON of the argument list with nested JSON strings decoded, and ours is the JSON of our argument dicts, which are already decoded.

Nothing in that score reads the answer. A run that called the right tools in the right order and named the wrong cause at high confidence passes theirs and lands negative on ours, and the eval report is meant to show those rows side by side.

## Reproducing a number

```
uv run python -m evals.grader evals/results/<run_id>/report.json
```

prints the arithmetic for a report, reading the scenario by the id the report carries and the window start from `gen/runs/<run_id>.json`. `--json` prints the full `Grade`.
